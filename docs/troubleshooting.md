# 문제 해결 기록

## 노드가 IP로 표시되는 문제

**현상**: Grafana 범례와 Alertmanager 메시지에 일부 노드가 `IP:9100` 형태로 표시되어 장애 대상을 빠르게 식별하기 어려웠습니다.

**원인**: node-exporter 시계열의 `instance` 라벨을 그대로 사용했고, 동적 인벤토리로 재생성된 노드의 사람이 읽을 수 있는 이름이 중앙 메트릭에 일관되게 전달되지 않았습니다.

**해결**: Prometheus 라벨과 Grafana 쿼리를 노드 이름 기준으로 정리하고, 표시 이름에는 hostname 라벨을 우선 사용하도록 수정했습니다. 서울·도쿄 환경에도 같은 규칙을 적용할 수 있게 리전 라벨과 분리했습니다.

## GitOps 태그 갱신이 CI를 다시 실행하는 문제

**현상**: Jenkins가 이미지 태그를 커밋하면 Webhook이 다시 파이프라인을 실행하여 동일 이미지를 반복 빌드할 수 있었습니다.

**해결**: 커밋 제목과 변경 파일을 확인하여 `gitops/` 전용 변경이면 소스 검증, 이미지 빌드, ECR Push, 태그 갱신 단계를 생략했습니다.

## 개발 브랜치에 Dockerfile이 없는 문제

**현상**: 일부 기능 브랜치는 서비스 전체 파일을 포함하지 않아 Docker 빌드를 전제로 한 CI가 실패했습니다.

**해결**: 브랜치에서 존재하는 Python 소스는 문법 검증하고, Dockerfile이 있는 구성요소만 빌드했습니다. 다만 `main`에서는 운영에 필요한 모든 필수 파일을 강제했습니다.

## 서울·도쿄 데이터가 섞이는 문제

**위험**: DR 복구 후 같은 메트릭·로그 저장소를 사용하면 리전 라벨이 없거나 잘못되었을 때 두 환경이 같은 대시보드에 섞일 수 있습니다.

**해결**: 공통 values 위에 도쿄 override를 마지막으로 적용하고, `cluster`와 `region` 라벨로 쿼리를 분리했습니다. 대시보드 제목과 태그도 서울·도쿄로 명확히 나눴습니다.

## 모니터링 Pod는 정상인데 중앙에 데이터가 없는 문제

**원인 후보**: 노드에서 중앙 서버로 접속되는 것만 확인하면, 실제 전송 주체인 Pod의 egress가 막힌 문제를 놓칠 수 있습니다.

**해결**: Helm 설치 전에 임시 Pod에서 중앙 Prometheus와 Loki의 Ready endpoint에 접근하도록 검사했습니다. 실패 시 설치를 중단하여 Running 상태만 정상이고 데이터는 유실되는 상황을 방지했습니다.

## 웹 Ingress와 초기 데이터 누락

**현상**: 매니페스트 구조를 GitOps로 이전하는 과정에서 웹 Ingress와 초기화 Job이 새 Kustomize 리소스 목록에 포함되지 않아 웹 접근과 행사 데이터가 누락되었습니다.

**해결**: Ingress와 초기화 리소스를 복구하고 base에서 함께 관리하도록 수정했습니다.
